# Gist Agent 数据分析链路改造规划

> 状态：分阶段实施中（Phase 0～5 已完成；下一阶段为 Phase 6 规模化优化）
>
> 最近复盘：2026-09-17
>
> 适用范围：API、Worker、LLM 编排、Prompt、上下文、记忆、SQL 执行、评测与可观测性

## 1. 文档目的

本目录记录当前数据分析 Agent 的架构复盘、决策理由、实施结果和验证证据。它不是功能介绍，也不只是任务清单。文档必须回答四个问题：原来为什么不够好、为什么选择当前方案、改完后具体好在哪里、还有哪些问题没有解决。

## 2. 阅读方式

文档分为三层，避免把“计划”和“已实现事实”混在一起：

1. `01～06` 是专题设计文档，解释问题域、现状证据和目标设计。
2. `07` 是交付路线图，解释为什么按 Phase 0～6 的顺序推进，以及每阶段的完成条件。
3. `08` 之后是阶段决策与实施记录，形成“问题 → 根因 → 方案取舍 → 实现 → 收益 → 验证 → 遗留项”的闭环；判断当前系统实际具备什么能力，应以这一层和代码为准。

建议新读者先阅读本页和 `07`，再按当前关心的 Phase 阅读对应实施记录；只有需要设计细节时再进入 `01～06`。

## 3. 总体判断

当前系统已经具备较好的工程骨架：API/Worker 分离、事务 Outbox、Redis Stream、generation 幂等、心跳与取消、AST SQL 只读校验、分层上下文压缩和结构化记忆治理。这些能力足以支持 Demo 和内部试用。

Phase 0～5 已经解决输入串话、假取消、终态后写入、非法工具调用、证据丢失、图表数值复制、SQL fail-open、截断结果误读和记忆不可治理等确定性问题。当前主要剩余问题是：

1. 大规模 Schema 检索、成本和延迟策略尚未完成。
2. 现有 benchmark 验证参考 SQL，不验证真实 Agent 回答质量。

| Phase 5 | 当前记忆缺少来源、版本、冲突和删除语义                  | 结构化 MemoryRecord 与 patch 协议          | 记忆可追溯、可纠正、可撤销                  | 大规模 Schema 与成本效率尚未优化   |
| Phase 6 | 全量 Schema 和固定策略在规模扩大后成本、延迟不可控      | 分层检索、模型路由、在线评估和保留策略     | 在质量门槛下控制成本并支持规模化运营        | 持续优化阶段，不代表系统永久“完成” |

## 6. 优先级摘要

### P0：先保证不会串话、不会“死后继续执行”

- 超时、取消和 ownership 丢失后，停止 LLM、SQL、事件发布和 checkpoint。
- generation 固化 `request_message_id`、`datasource_id` 和上下文水位。
- 同一 conversation 默认串行；未来若开放并行，必须基于分支/父消息建模。
- Agent 达到最大迭代次数时必须失败或进入明确的受控收尾，不能静默成功。

### P1：建立可信的分析执行模型

- 用状态机代替纯 Prompt 工作流。
- 查询结果保存为 artifact，图表直接消费 artifact。
- 上下文按完整 Turn 组织，不再按单条消息独立裁剪。
- SQL 安全从 AST 单层防线升级为应用校验 + 数据库只读角色 + statement timeout。
- 建立真正执行 Agent 的离线评测。

### P2：提高规模化质量与成本效率

- Schema 分层检索，避免全量 Schema 永久注入。
- 记忆分类、版本化、可纠正、可遗忘。
- Prompt、模型、工具和上下文策略统一版本化。
- 完善质量、成本、延迟和恢复指标。

## 7. 建议目标链路

```text
接收请求
  -> 固化 generation 输入快照
  -> 会话级排队/分支校验
  -> 构建受控上下文
  -> 理解问题与确认口径
  -> 制定查询计划
  -> SQL 校验与执行
  -> 生成 Query Artifact
  -> 结果质量检查
  -> 结论生成
  -> 可选 Chart Artifact
  -> 原子化提交消息与终态
  -> 异步、版本化更新记忆
```

## 8. 决策原则

- Prompt 负责语义判断，代码负责权限、顺序、状态和不变量。
- 模型输出是候选，不是事实；数据结论必须能追溯到查询证据。
- 对话历史用于交流连续性，artifact 用于证据连续性，memory 用于稳定偏好和口径。
- 任何终态都必须是副作用边界；终态之后不得继续写消息、发普通事件或执行查询。
- 安全检查无法证明安全时必须拒绝执行，即 fail closed。
- 先建立评测与版本基线，再进行大规模 Prompt 调优。

## 9. 阶段文档质量标准

每份 Phase 实施记录都必须包含：

1. 阶段结论和范围；
2. 重构前的行为、代码证据和业务风险；
3. 根因，而不只描述症状；
4. 至少一个备选方案及未采用原因；
5. 最终方案和关键不变量；
6. 重构前后对比及收益成立的因果链；
7. 自动化验证证据；
8. 非目标、遗留风险和下一阶段承接关系；
9. 迁移、兼容和回滚说明。

“增加了某个类/字段/测试”不是完整说明；文档必须同时解释它防住了什么失败模式，以及为什么测试足以证明相应不变量。

计划中的 Phase 在编码前还必须具备一份实施合同，至少明确：输入与输出契约、实施步骤、数据库迁移顺序、兼容/双写/回滚路径、自动化测试矩阵、人工验收边界、开始条件、完成条件和明确非目标。存在未决选择时必须先记录决策负责人和截止点，不能在实现中临场决定。
