# 产品目标与已确认决策

2026-09-23 用户决定将业务定义改为按数据源保存的文本记忆，明确“记住：”直接保存，对话提炼候选仍需确认；此决策覆盖下表 D04～D07 的结构化业务定义表述。当前实现和验收状态见[交付与验证](05-delivery-and-validation.md)。2026-09-21 用户要求直接切换唯一新核心；2026-09-22 明确取消旧对话、旧记忆及旧结构兼容。这两项后续决策覆盖原有双核过渡与历史数据保留安排，但不取消权限、隔离、取消和多会话恢复边界。过程见[历史归档](../archive/2026-09-agent-refactor.md)。

## 1. 成功标准

用户能围绕一个问题连续分析，知道本次使用的业务口径，检查关键结论依据；当结果不可靠或调查未完成时，系统明确暴露限制。开发者能解释模型如何选择行动、代码如何限制行动、上下文为何保留或舍弃信息，以及失败如何改变下一步。

首期不以生产平台完备性、Agent 数量、配置项数量或代码规模衡量深度。

## 2. 已确认决策清单

| ID | 已确认决策 | 必须体现的实现边界 |
| --- | --- | --- |
| D01 | 学习优先，求职成果作为表达 | 亮点必须绑定失败案例和可检查结果 |
| D02 | 准确问数打底，有限自主诊断为主 | 不要求每次找出原因，不做开放式无限调查 |
| D03 | 单 Agent 选择路径，代码守边界 | 不预设 Planner/Executor/Reviewer，不硬编码诊断维度顺序 |
| D04 | 关键业务约定来自数据源记忆或用户澄清 | 字段、样本和 Schema AI 注释不能自动变成业务事实 |
| D05 | 数据源记忆独立模块 | 保留数据源管理；记忆有独立页面、接口和表 |
| D06 | 长期记忆按数据源保存 | 明确“记住：”直接保存；模型提炼的候选经用户确认 |

| D09 | 每会话一个当前分析任务 | 连续追问更新状态；改变条件后检查证据适用性，不做任务分支管理 |

| D11 | 关键结论关联可展开证据 | 可查看口径、条件、SQL、结果；不做逐数字自动核验 |

| D14 | 按新设计重写 Agent 核心 | 保留外围模块，不维护两套记忆事实源，不整体重写应用 |
| D15 | 保留 API/Worker 外壳 | 核心不感知队列/心跳，不扩展复杂恢复，不删除既有有效机制 |

| D17 | SQL 修复回到主循环 | 工具内部不得调用模型改写 SQL，错误和修改可追踪 |
| D18 | 固定优先级上下文、按需读证据 | 不迁移旧三级历史压缩，不增加摘要 Agent 或向量记忆 |
| D19 | 保留已有工程与外围能力，不调整技术栈 | 遵守下方保留红线，核心重写不得造成外围能力退化 |
| D20 | 多会话切换与流式恢复不退化 | 切走后台继续生成，切回补齐内容并继续接收，无串话、重复或误取消 |

## 2.1 已有能力保留红线

| 范围 | 本次要求 |
| --- | --- |
| API / Worker、队列、Outbox、generation 生命周期 | 保留现有工程架构，新核心通过适配层接入；不因核心重写改为前端连接驱动执行 |
| 多会话与流式体验 | 切走不取消后台生成；切回能补齐遗漏内容，并在任务仍运行时继续接收流式事件 |
| SSE、持久化、隔离与取消 | 保留重连、有序恢复、消息持久化、会话隔离、显式取消和终态写保护 |
| 数据源、认证、上传、表管理 | 保留既有功能与入口；业务定义是独立新增模块 |
| 技术栈与部署架构 | 不调整现有前后端框架、数据库、队列/SSE 技术选型及部署架构；新增模块和兼容性迁移不等于更换技术栈 |

以上保留要求不意味着所有旧 Agent 内部实现不动。允许替换的范围仍为旧分析循环、Prompt/上下文组织、通用记忆与后台蒸馏、隐藏 SQL 模型修复；必要的外围适配必须保持既有用户行为。

“复杂恢复不作为本轮目标”仅表示不新建或扩展该能力，不授权删除已经工作的恢复机制。若实现发现必须牺牲既有能力或更换技术栈，应先说明具体原因并与用户重新确认，不能归入普通实现细节。

## 3. 业务主场景

主场景：比较两段明确时间范围的 7 日激活率，检查成熟观察窗口，分析渠道结构和渠道内部变化，针对主要解释验证，再回答“只看 Android”“本次改用另一口径”等追问。

必须先检查数据是否支持平台筛选：存在平台字段不代表存在经过确认的注册平台或用户平台定义。缺少映射时澄清或说明无法完成，不凭事件平台猜注册平台。

挑战场景：活跃下降是否来自采集缺口；是否存在重复事件或汇总与明细差异。先判断证据是否可信，再解释业务变化。

不预设数据中一定存在激活下降或某渠道一定是原因。固定比较区间必须由标准查询确认；如果没有下降，正确行为就是纠正问题前提。

## 4. 值得做深的亮点

| 亮点 | 实际难点 | 可演示证据 |
| --- | --- | --- |
| 受控自主诊断 | 行动合法不等于判断正确，何时验证和停止 | 一个解释被证据支持或推翻；无证据时停下 |
| 可维护业务口径 | 数据源归属、用户确认、临时覆盖与版本变更 | 改定义后下一轮生效，历史答案仍能解释旧口径 |
| 多轮证据连续性 | 条件变更后识别旧证据失效 | Android 追问触发必要重查，纯重画图复用原结果 |
| 可检查的上下文 | token 有限时保留任务与事实依据 | 同快照同选择，展示省略原因和按需回读 |
| 可追溯结论与主循环纠错 | 证据引用有效不等于语义充分，修复不能隐藏 | SQL 错误—修正—验证—带引用回答的完整记录 |

Prompt 快照解释“输入是什么”，工具记录解释“发生了什么”；不宣称能还原模型内部思维。展示行动说明和证据，不展示原始推理链。

## 5. 非目标

多 Agent、向量 RAG、通用长期记忆、后台记忆蒸馏、模型自动路由、逐数字核验、可执行指标 DSL、百表规模优化、大型评测平台、生产 dashboard、成本价格维护、跨机恢复和完整发布工程均后置。

保留 SQL 安全、权限、超时取消、会话隔离和终态写入边界；“不扩展生产能力”不意味着移除这些底线。

## 6. 变更准入

新增机制先给出失败案例，再说明最小替代方案为什么不足、如何验证、将移除或替代什么。不能仅因“更完整”“业界通常有”加入主线。

本方案中的阶段拆分、工具名、字段和预算默认值属于实施约定。用户未逐项确认这些细节；实现者可在不改变 D01～D20 的前提下调整，但必须说明理由并同步文档，不能自行升级为新的产品范围。
